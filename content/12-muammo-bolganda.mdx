# Muammo bo'lganda

Xato har kimda bo'ladi. Muammo xatoning o'zida emas, uni yashirishda yoki shoshib tuzatishda. Bu bob eng ko'p uchraydigan holatlar uchun tayyor tartib beradi.

Uchta umumiy qoida bor: vahima qilmang, himoyalangan branch tarixini qayta yozmang, darhol xabar bering.

## Kimga va qanday aytish kerak

Ba'zi muammolar faqat sizning branch'ingizga tegadi. Ularni o'zingiz hal qilasiz. Boshqalari `dev`, `beta`, `main` yoki muhitlarga tegadi. Ular haqida jamoa bilishi shart.

<Band id="UM-11" />

Xabarda to'rt narsa bo'ladi:

1. Nima bo'ldi.
2. Qachon va qaysi commit yoki PR'dan keyin.
3. Siz nima qildingiz.
4. Hozir nima kerak.

<Phrase ok="Beta qizil: #172 Bildirishnomalar merge'dan keyin test yiqildi. Revert PR ochdim, review kerak." bad="Beta'da nimadir buzildi shekilli.">

Aniq xabar tuzatishni tezlashtiradi. Taxmin emas, fakt yozing.

</Phrase>

## Xato commit dev yoki beta'da: revert

`dev` yoki `beta`ga xato commit kirdi. Uni tarixdan o'chirib bo'lmaydi: boshqalar allaqachon shu tarixni fetch qilgan. To'g'ri yo'l — <Term t="revert" />. U xato commit'ning teskarisini yangi commit qilib qo'shadi.

<Band id="UM-T2" />

<Steps>

1. Xato commit'ning hash'ini toping: `git log --oneline origin/dev`.
2. `origin/dev`dan revert branch'ini oching. Nomi: `<tiket raqami>-revert-<qisqa-nom>`.
3. Revert qiling: `git revert <hash>`.
4. Push qiling va PR oching. PR tavsifida sababni yozing.
5. Review'dan keyin PR'ni `dev`ga merge qiling.
6. Release owner'ga ayting. U promote qiladi.

</Steps>

<Terminal>{`
$ git fetch origin
$ git switch -c 172-revert-notification-recipients --no-track origin/dev
$ git revert 4b7c1d3
[172-revert-notification-recipients 9e1f0a2] Revert "feat(notifications): ..."
$ git push
`}</Terminal>

<Note>

Squash-merge bo'lgan PR `dev`da bitta commit bo'ladi. Shuning uchun butun PR'ni bitta `git revert` bilan qaytarish mumkin.

</Note>

## Qizil beta

Beta qizil — bu oxirgi promote'dan keyin CI yoki deploy muvaffaqiyatsiz tugagani. Qizil beta keyingi release'ni to'sadi.

<Band id="BETA-01" />

<Steps>

1. CI log'ini o'qing va qaysi qadam yiqilganini toping.
2. Sababchi commit'ni toping. Odatda bu oxirgi promote'dagi commit'lardan biri.
3. Tuzatish bir soatdan kam vaqt olsa, tuzatish tiketi va PR'ini oching (BETA-03).
4. Aks holda sababchi commit'ni revert qiling.
5. Tuzatish ham, revert ham oddiy yo'ldan yuradi: PR, `dev`, promote.

</Steps>

<Band id="PROMOTE-T1" />

## Prod'dagi muammo: rollback, keyin hotfix

Prod'da muammo bo'lsa, ikki ish bor: foydalanuvchini himoya qilish va xatoni tuzatish. Tartibi muhim: avval himoya.

<Term t="rollback" /> muhitni oldingi ishlagan versiyaga qaytaradi. U kod tarixini o'zgartirmaydi. <Term t="hotfix" /> esa xatoni kodda tuzatadi.

<Steps>

1. Release owner'ga darhol ayting.
2. Release owner rollback qiladi. Tartibi repo profilida yoziladi.
3. Xatoni oddiy yo'l bilan tuzating: tuzatish PR'i, `dev`, promote, beta yashil.
4. Release owner release window'dan tashqarida release PR ochadi.
5. Agar kutish mumkin bo'lmasa, release owner favqulodda hotfix tartibini qo'llaydi. Bu tartib repo profilida yoziladi.
6. Favqulodda hotfix'dan keyin `main` darhol `dev`ga PR orqali (merge commit bilan) qo'shiladi va promote qilinadi (PROD-05).
7. Hotfix ham release kabi yoziladi: tag va GitHub Release, tiket yopiladi (PROD-06).

</Steps>

<Band id="PROD-03" />

<Warning>

6-qadamni tashlab ketmang. Aks holda hotfix faqat `main`da qoladi va keyingi release uni yo'qotadi.

</Warning>

## Sir commit qilinib push bo'lgan

Kalit, parol yoki token commit'ga tushib, push qilindi. Endi u boshqa nusxalarda, CI cache'ida va fork'larda bo'lishi mumkin. Tarixni qayta yozish bu nusxalarni o'chirmaydi.

<Warning>

Birinchi qadam — kalitni almashtirish. Koddan o'chirish keyin. Eski kalit ochiq deb hisoblanadi.

</Warning>

<Steps>

1. Kalitni xizmatning o'zida bekor qiling va yangisini yarating.
2. Release owner'ga ayting.
3. Yangi kalitni serverlarga qo'ying.
4. Sirni koddan olib tashlang va env kalitiga o'tkazing. Bu oddiy PR bilan bo'ladi.

</Steps>

<Note>

Sir hali push qilinmagan bo'lsa, ish osonroq. O'z branch'ingizda `git commit --amend` yoki `git reset` bilan commit'ni tuzating. Bu holatda kalitni almashtirish shart emas.

</Note>

## Commit noto'g'ri branch'da

Siz local `dev`da yoki boshqa tiketning branch'ida commit qildingiz. Commit hali push qilinmagan.

<Steps>

1. Joriy holatdan to'g'ri branch oching: `git switch -c 180-to-gri-nom`. Commit yangi branch'da qoladi va siz endi shu branch'dasiz.
2. Local `dev`ni remote holatiga qaytaring, `dev`ga o'tmasdan: `git branch -f dev origin/dev`.

</Steps>

<Note>

`git branch -f` faqat local branch ko'rsatkichini suradi: ish papkasiga va remote'ga tegmaydi. `git reset --hard` esa commit qilinmagan o'zgarishlarni o'chiradi, shuning uchun protocol uni ishlatmaydi (GIT-02).

</Note>

Commit boshqa tiketning branch'iga tushgan bo'lsa, uni to'g'ri branch'ga <Term t="cherry-pick" /> qiling. Keyin eski branch'dan olib tashlang. Eski branch push qilingan bo'lsa, keyingi push `--force-with-lease --force-if-includes` bilan bo'ladi.

## Rebase buzildi yoki commit yo'qoldi: reflog

Rebase paytida chalkashib ketsangiz, rebase'ni to'xtating:

<Terminal>{`
$ git rebase --abort
`}</Terminal>

Branch rebase'dan oldingi holatiga to'liq qaytadi. Rebase tugagan bo'lsa ham eski holat yo'qolmaydi. <Term t="reflog" /> HEAD qayerda bo'lganini eslaydi. Git rebase'dan oldingi joyni `ORIG_HEAD`da ham saqlaydi.

<Terminal>{`
$ git reflog -8
9e1f0a2 HEAD@{0}: rebase (finish): returning to refs/heads/172-notification-recipients
4b7c1d3 HEAD@{1}: rebase (pick): feat(notifications): oluvchilar moduli
c5d2e91 HEAD@{2}: rebase (start): checkout origin/dev
7aa0c51 HEAD@{3}: commit: feat(notifications): oluvchilar moduli
`}</Terminal>

<Steps>

1. `git reflog` bilan rebase'dan oldingi commit'ni toping. Misolda bu `HEAD@{3}`.
2. Avval uni xavfsiz joyga saqlang: `git branch rescue-172 7aa0c51`.
3. `git log rescue-172` bilan to'g'ri commit ekanini tekshiring.
4. Ishni shu branch'dan davom ettiring: `git switch rescue-172`.

</Steps>

<Warning>

Tiklangan branch push qilingan branch o'rnini bossa, keyingi push `--force-with-lease --force-if-includes` bilan bo'ladi (GIT-06).

</Warning>

Yo'qolgan commit uchun ham shu yo'l ishlaydi. Reflog faqat local'da va odatda 90 kun saqlanadi.

## Himoyalangan branch'ga xato push

Siz `dev`, `beta` yoki `main`ga tasodifan push qildingiz. Odatda hook buni to'xtatadi, lekin hook har doim ham ishlamaydi.

<Band id="UM-T2" />

<Steps>

1. Boshqa hech narsa qilmang.
2. Release owner'ga darhol ayting: qaysi branch, qaysi commit.
3. Release owner qaror qiladi: commit qoladi yoki revert qilinadi.
4. Revert kerak bo'lsa, «Xato commit dev yoki beta'da» bo'limidagi tartib ishlatiladi.

</Steps>

## Pull rad etildi: «Not possible to fast-forward»

`git pull` shu xabar bilan to'xtadi. Demak, local branch va remote branch ajralgan: ikkalasida ham boshqasida yo'q commit'lar bor. `pull.ff=only` sozlamasi bu holatda merge commit yaratmasdan to'xtaydi.

Nima qilish branch turiga bog'liq.

| Branch | Sabab | Nima qilish kerak |
|---|---|---|
| O'z feature branch'ingiz | `dev`ga yangi commit'lar kirdi | `git fetch origin` va `git rebase origin/dev`. |
| Local `dev` yoki `beta` | Siz unda commit qilgansiz | Commit'larni yangi branch'ga ko'chiring, keyin `git branch -f dev origin/dev`. «Commit noto'g'ri branch'da» bo'limiga qarang. |

<Phrase ok="Pull rad etildi, local dev ajralib qolgan ekan. Commit'ni yangi branch'ga ko'chirdim." bad="Pull ishlamayapti, git buzildi.">

Git buzilmagan: u sizni tasodifiy merge commit'dan himoya qildi.

</Phrase>

## Eslab qoling

- Himoyalangan branch yoki muhitga tegadigan muammo — avval release owner'ga xabar.
- `dev`, `beta`, `main`da hech qachon reset yoki force-push yo'q. Faqat revert.
- Qizil beta o'sha kuni tuzatiladi yoki revert qilinadi.
- Prod: avval rollback, keyin hotfix. Favqulodda hotfix'dan keyin `main` `dev`ga merge qilinadi.
- Sir push bo'lsa — avval kalitni almashtiring.
- Rebase buzilsa — `git rebase --abort`. Tugagan bo'lsa — `git reflog`.
- `git reset --hard` o'rniga zaxira branch va `git branch -f` (GIT-01, GIT-02).
